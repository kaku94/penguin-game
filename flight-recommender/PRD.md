# PRD: 항공권 추천 챗봇 (가칭 "적당항공")

- 작성일: 2026-10-22
- 작성자: dbinc.edu1
- 상태: Draft v0.4 (Vercel + Supabase 배포 구조)

---

## 1. 배경 및 문제

여행을 떠올릴 때 질문은 보통 이렇게 생긴다:

> "맛집투어하러 1박2일 평일에 일본 여행갈려는데 11월중에 싼 항공권 있나?"

기존 항공권 검색 사이트는 **정확한 출발지·도착지·날짜**를 넣어야 한다. 그래서 "일본 어디든", "11월 평일 아무 때나", "1박2일"처럼 열린 조건이면 도시와 날짜 조합을 사람이 직접 수십 번 검색해야 한다. 가격만 볼 뿐, "1박2일인데 현지에 몇 시간 있을 수 있나" 같은 실제 효율도 따로 따져야 한다.

## 2. 목표

자연어 질문 하나로 **목적·기간·예산에 맞는 항공권 후보 3~5개**를 추천 이유, 예약 링크와 함께 1분 안에 받는다.

### 성공 지표 (개인용 기준)
| 지표 | 목표 |
|---|---|
| 응답 시간 (질문 → 최종 추천) | P90 60초 이내 |
| 추천 가격 정확도 (예약 사이트에서 직접 확인 시 ±10% 이내) | 80% 이상 |
| 쿼리당 비용 | 월 운영비 1만원 이하를 지키는 수준 (§9 참고) |
| 재검색 없이 쓸 만한 후보가 나온 비율 | 70% 이상 (본인 체감) |

### 비목표 (Non-goals)
- 앱 안에서 직접 결제·발권하지 않음 (예약 사이트 링크까지만 제공)
- 일반 공개 서비스, 회원가입, 수익화
- 숙소·맛집 추천 (MVP 이후로도 우선순위 낮음)
- 가격 알림, 검색 히스토리 (MVP 범위 아님)

## 3. 사용자

- **주 사용자**: 본인 + 초대받은 지인 소수 (~10명)
- **상황**: 단거리 해외(일본·동남아 등) 짧은 여행을 즉흥적으로 계획. 날짜와 도시는 정하지 않았고 "싸고 알차게"가 핵심.

## 4. 핵심 사용자 시나리오

**S1. 열린 조건 검색 (대표 시나리오)**
1. 사용자가 웹 채팅창에 입력: "맛집투어하러 1박2일 평일에 일본 여행갈려는데 11월중에 싼 항공권 있나?"
2. 시스템이 조건을 해석해 보여줌:
   - 출발: 프로필 기본값(예: ICN, GMP)
   - 목적지: 일본 → 맛집투어에 맞는 후보 도시 **오사카·후쿠오카·도쿄** (+ 이유 한 줄)
   - 기간: 2026-11-01 ~ 11-30, 평일 출발·평일 귀국, 1박
   - 우선순위: 가격 + 체류시간 효율
3. 진행상황 스트리밍: "오사카 검색 중… 후쿠오카 검색 중…"
4. 결과 카드 3~5개 (예시):
   - 🥇 **후쿠오카 · 11/18(화)~11/19(수) · 왕복 약 12만원**
     가는 편 07:30 ICN→FUK / 오는 편 20:40 FUK→ICN · 현지 체류 약 34시간
     "가장 싸고, 아침 출발·저녁 귀국이라 1박2일에 최적" · [예약 링크]
5. 사용자가 링크로 예약 사이트에 가서 직접 확인하고 결제.

**S2. 후속 대화로 조건 수정 (MVP 직후 단계)**
- "금요일은 빼줘", "더 싼 거 없어?", "오사카만 다시 봐줘" → 이전 조건을 유지한 채 재검색.

## 5. 기능 요구사항

### 5.1 MVP (P0)
| ID | 기능 | 설명 |
|---|---|---|
| F1 | 자연어 조건 파싱 | 질문에서 목적, 목적지(국가/도시), 기간(월·요일·박수), 예산, 인원을 추출. 빠진 값은 프로필 기본값으로 채우거나 합리적으로 가정하고, 가정한 내용을 화면에 표시 |
| F2 | 목적지 확장 | 국가·지역 단위 목적지는 여행 목적에 맞는 후보 도시 2~4개로 확장 (예: 맛집→오사카/후쿠오카/도쿄, 온천→후쿠오카/삿포로). **(국가, 목적) → 후보 도시 매핑 테이블**을 우선 쓰고, 테이블에 없는 조합만 LLM이 고름. LLM이 고른 결과는 로그로 남겨 테이블에 추가할 후보로 검토 |
| F3 | 날짜 조합 생성 | 조건에 맞는 출발·귀국일 조합 생성 (예: 11월 평일 1박2일 → 월-화, 화-수, 수-목, 목-금). 1분 안에 끝나도록 검색 횟수에 상한을 둠 |
| F4 | 웹 검색 기반 가격 수집 | Claude API의 웹 검색 도구로 항공권 가격과 운항 시간 정보를 수집. 가격마다 출처 URL과 수집 시각을 기록 |
| F5 | 랭킹 | 가격 + 시간대 효율로 점수 계산 (§6) |
| F6 | 추천 카드 표시 | 도시·날짜·**출발 공항(ICN/GMP 강조 표시)**·편명/시간·**1인 왕복 가격**·현지 체류시간·**위탁수하물 포함 여부**·추천 이유·예약 링크. 인원이 2명 이상이어도 1인 가격만 표시 |
| F7 | 예약 링크 | 출처 링크와 함께 해당 조건이 미리 입력된 검색 링크(Google Flights, 스카이스캐너, 네이버 항공권 등) 제공 → 사용자가 직접 검증 |
| F8 | 진행상황 스트리밍 | 검색 단계를 실시간 표시해 체감 대기시간 줄이기 |
| F9 | 프로필 | 사용자별 기본 출발 공항(복수 가능), 선호 항공사 유형(LCC/FSC 무관 기본) 저장 |
| F10 | 접근 제어 | 초대코드/공유 비밀번호 입력 후 사용. 코드별 일일 쿼리 한도 (예: 20회) |

## 6. 추천 로직

**점수 = w₁ · 가격점수 + w₂ · 시간효율점수** (기본 w₁=0.6, w₂=0.4)

- **가격점수**: 후보 중 최저가 대비 상대값 (1인 왕복 운임, 세금·유류할증료 포함, 위탁수하물 미포함 기준)
- **시간효율점수**: 현지 체류 가능 시간 ÷ 전체 여행 기간 (항공편 시각 기준, 집→공항 이동시간은 반영하지 않음)
  - 가는 편: 이른 출발일수록 가점 (예: 10시 이전 도착 최고점)
  - 오는 편: 늦은 출발일수록 가점 (예: 18시 이후 출발 최고점)
  - 새벽 1~5시 출발/도착은 감점
- 경유편은 기본 제외 (단거리 1박2일 기준)
- 같은 도시+날짜 조합은 최고 점수 1개만 노출해 결과 다양성 확보
- 결과마다 "왜 추천했는지"를 한 문장으로 생성

## 7. 시스템 구성 (초안)

```
[웹 채팅 UI] ──SSE 스트리밍──▶ [백엔드 API]
                                    │
                         ┌──────────┴──────────┐
                  [조건 파싱/계획]        [검색 실행기]
                   (Claude, 저비용 모델)   Claude + web_search 도구
                                          도시×날짜 병렬 실행, 상한 N회
                                    │
                              [랭킹 엔진] (코드, 결정적 계산)
                                    │
                              [응답 생성] → 추천 카드 JSON
                                    │
                           [캐시] 같은 노선·날짜 6시간 TTL
```

- **기술 스택**: Next.js (React UI + API Routes, TypeScript), Vercel 배포, DB Supabase Postgres, API 문서 Swagger UI(`/docs`). v0.3의 Spring Boot + SQLite 서버는 Vercel 배포를 위해 대체함
- **LLM**: Claude API (`@anthropic-ai/sdk`). 파싱용·검색용 모델을 환경변수(`PARSE_MODEL`, `SEARCH_MODEL`)로 따로 둠. 기본값은 Claude Opus 5.5이고, M0 결과를 보고 비용·품질에 따라 Haiku 5.5 등으로 내릴지 결정
- **후보 도시 선정은 질문 해석과 한 번에**: 해석 호출이 후보 도시도 함께 제안하고, 관리 테이블에 없는 경우만 그 제안을 씀 (LLM 호출 1회 절약)
- **추천 이유 문구는 코드 템플릿으로 생성**: 랭킹 점수 구성요소(최저가 대비 %, 체류시간, 시간대)로 만들어 추가 LLM 호출 없음
- **랭킹은 LLM이 아닌 코드로 계산**해 결과가 재현되고 디버깅하기 쉽게 함. LLM은 가격·시간을 구조화된 데이터로 뽑는 역할만 맡음.
- **캐시**: 비용과 속도를 위해 (출발, 도착, 날짜) 키로 검색 결과를 몇 시간 캐시.
- **배포**: Vercel 무료 플랜(함수 최대 60초 → 검색 제한시간 50초) + Supabase 무료 플랜에 초대코드·프로필·도시 매핑·캐시·검색 기록 저장. 테이블은 RLS로 막고 서버만 Postgres 직접 연결(`POSTGRES_URL`)로 접근. 스키마는 서버가 처음 DB를 쓸 때 자동 적용

## 8. 비기능 요구사항
- **성능**: P90 60초 이내. 넘으면 그때까지 모인 결과로 부분 응답하고 "추가 검색" 버튼 제공.
- **신뢰성 표시**: 모든 가격에 "웹 검색 기준 추정가 · 수집 시각" 표기. 확정가가 아님을 명시.
- **보안**: API 키는 서버에만 둠. 초대코드별 레이트 리밋으로 비용 폭주 방지.
- **언어**: 한국어 UI·응답, 통화는 KRW.

## 9. 비용 가드레일 (월 1만원 이하 목표)
- 쿼리당 웹 검색 호출 상한 (예: 최대 8회): 도시 3개 × 대표 날짜 조합 위주
- 캐시 적중 시 검색 생략
- 초대코드별 일일 한도, 전체 월 예산을 넘으면 서비스 일시 중단
- 실제 API 단가는 구현 시점의 Anthropic 가격표로 다시 계산해 상한값 조정 (TBD)

## 10. 리스크 및 대응
| 리스크 | 영향 | 대응 |
|---|---|---|
| 웹 검색으로는 날짜별 실시간 가격을 정확히 얻기 어려움 | 추천 가격 부정확 | 추정가로 표기 + 조건이 채워진 검색 링크로 사용자 검증. 정확도가 부족하면 항공권 API(Amadeus 등)로 교체할 수 있게 검색 계층을 인터페이스로 분리 |
| 사이트 약관·스크래핑 제한 | 데이터 수집 차단 | 직접 스크래핑 대신 검색 도구 결과만 사용, 개인용 소량 트래픽 유지 |
| 1분 제한 vs 넓은 탐색 | 좋은 날짜를 놓침 | 저가 요일(화·수) 우선 탐색 휴리스틱, 부분 응답 + 추가 검색 |
| LLM 환각(없는 편명·가격) | 신뢰 하락 | 출처 URL이 없는 가격은 버림. 구조화 출력 스키마로 검증 |

## 12. 결정 사항 (v0.2)
| 질문 | 결정 | 근거 |
|---|---|---|
| 인천·김포 출발 시 공항 이동시간 반영? | 랭킹에는 반영 안 함, 카드에 출발 공항만 강조 표시 | 사람마다 이동시간이 달라 일괄 보정이 부정확. 사용자가 보고 직접 판단 |
| 2명 이상일 때 가격 표시 | 1인 가격만 | 가장 단순하고 항공권 사이트 표기 관행과 같음 |
| 위탁수하물 비용 | 미포함 기준, 카드에 포함 여부만 표기 | 1박2일은 기내수하물로 충분한 경우가 많고, 수하물 요금까지 검색하면 1분 제한과 비용 한도를 넘김 |
| 목적별 후보 도시 선정 | 관리 테이블 우선 + 없는 조합만 LLM 폴백 | 자주 쓰는 조합은 결과가 일관되게, 새로운 목적도 처리 가능 |

## 13. 남은 열린 질문
- 인원이 많을 때 잔여석 부족(1인 최저가 좌석이 인원수만큼 없음) 가능성을 안내할지?
- 매핑 테이블 초기 데이터(국가 × 목적) 범위: 일본·동남아 몇 개 목적부터 시작할지?
